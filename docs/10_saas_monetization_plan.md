# [비즈니스 & 아키텍처 기획서] go-watchdog의 SaaS형 상용화 및 수익화 전환 계획

본 문서는 단일 서버 관제 시스템인 `go-watchdog`을 현대적인 멀티테넌트(Multi-tenant) SaaS형 API 가용성 모니터링 서비스(예: UptimeRobot, Better Stack 등)로 고도화하여 실제 비즈니스 모델로 수익화하기 위한 사업성 분석 및 기술 전환 계획서입니다.

## 2. SaaS 플랫폼 전환을 위한 기술적 아키텍처 고도화

현재 단일 사용자 타겟의 `go-watchdog`을 불특정 다수가 동시에 사용하는 글로벌 클라우드 서비스로 확장하려면 시스템 아키텍처를 다음과 같이 확장 리팩토링해야 합니다.

### 2.1 데이터베이스 구조 확장 (SQLite ➡️ PostgreSQL)
* **한계:** 현재의 SQLite는 단일 파일로써 다수의 동시 사용자가 대량의 가용성 로그를 쓸 때 데이터베이스 락(Lock) 및 성능 저하가 발생합니다.
* **대안:** 멀티테넌트 동시 처리에 강한 **PostgreSQL** 또는 분산 분할(Sharding)이 용이한 **MySQL**로 이전합니다.
* **유저별 격리:** 모든 테이블에 `user_id` 컬럼을 매핑하여 사용자 간의 데이터 접근 권한을 철저히 분리합니다.

```text
[Users] 1 : N [Health_Targets] 1 : N [Health_Logs]
   |
   |-- 1 : N [Subscriptions (결제/요금제 정보)]
```

### 2.2 인증 및 권한 관리 시스템 (Auth)
* 사용자 회원가입, 로그인, 소셜 인증(Google, GitHub 등 OAuth2)을 관리하는 보안 토큰(JWT) 기반 인증 레이어를 추가합니다.
* 로그인 세션에 연동하여 요금제 한도(예: 무료 사용자가 3번째 URL을 등록하려 할 때 결제 페이지로 리다이렉트)를 API 게이트웨이 및 백엔드 레벨에서 체크(Rate Limiting)합니다.

### 2.3 분산 헬스체크 노드 (Distributed Monitoring Nodes)
* **이유:** 수천 명의 사용자가 등록한 수만 개의 URL을 한 대의 수집 서버가 전부 핑을 날리는 것은 물리적으로 불가능하며, 수집 서버의 네트워크 지연이 서비스 상태를 오진(False Alert)하게 할 수 있습니다.
* **대안 (분산 체크):** 
  * Go로 작성된 초경량 **체크 노드(Checker Agent)**를 세계 주요 클라우드 리전(AWS/OCI의 서울, 도쿄, 미국, 독일 등)에 각각 1대씩 배치합니다.
  * 중앙 서버는 DB에 등록된 타겟 작업을 노드들에게 분배하고, 노드들은 독립적으로 HTTP 요청을 수행한 뒤 결과만 중앙 서버 API로 전송하거나 MQ(Message Queue)에 적재합니다.

### 2.4 대용량 알림 비동기 큐 시스템 (Message Queue)
* 특정 시점에 대규모 IDC 장애 등으로 수백 개의 서비스가 동시에 다운되면, 수천 건의 알림 요청이 한순간에 폭증합니다.
* 이로 인해 서버가 다운되거나 알림 전송이 누락되지 않도록 **RabbitMQ** 또는 **Redis Queue**를 도입하여 알림 처리를 백그라운드 워커(Worker) 풀에서 분산 처리하도록 설계합니다.

### 2.5 Stripe 결제 및 결제 연동 (Billing Integration)
* SaaS 결제의 글로벌 표준인 **Stripe API**를 연동하여 정기 결제(Subscription Billing), 영수증 발급, 카드 유효기간 만료 시 자동 재시도 등을 자동화 처리합니다.

## 3. 역할 분리 아키텍처 상세 설계 (Go Checker vs SaaS Web Portal)

SaaS 시스템의 고성능 및 확장성을 확보하기 위해, 물리적 모니터링을 담당하는 핵심 엔진(Go Checker)과 일반 유저들이 마주하는 관리자 페이지(Web Portal)를 완전히 격리(Decoupling)하여 독립적으로 구현합니다.

### 3.1 시스템 분리 다이어그램

```text
+-----------------------+      (API 요청)      +---------------------------------+
|  고객용 웹 프론트엔드  | -------------------> |    중앙 Web/API 메인 서버       |
|  (React/Vue 포털)     |                      | (Stripe 결제, 알림 발송, 인증) |
+-----------------------+                      +---------------+-----------------+
                                                               |
                                                  (Read/Write) v
                                               +-------------------------------+
                                               |  중앙 Database (PostgreSQL)  |
                                               +-------------------------------+
                                                               ^
                                                 (결제/로그)   | (체크 대상 로드 및 결과 적재)
                                                               |
                                            +------------------+------------------+
                                            |                                     |
                                 +----------+----------+               +----------+----------+
                                 |   Go Checker #1     |               |   Go Checker #2     |
                                 |  (서울 리전 노드)    |               |  (미국 리전 노드)    |
                                 +---------------------+               +---------------------+
```

### 3.2 역할 정의 및 기능

#### 1) Go Checker (경량 가용성 측정 엔진)
* **기능:** 수집 서버 내부의 웹 UI, API 핸들러, 설정 로더 등을 완전히 걷어내고 **오직 주기적 HTTP 핑 및 가용성 상태 측정만 담당하는 초경량 데몬(Daemon)으로 단순화**합니다.
* **배포:** 오라클 클라우드(OCI), AWS 등 주요 글로벌 클라우드 리전에 여러 대 배치하여 다중 교차 검증을 수행합니다.

#### 2) SaaS Web Portal (웹 API 메인 서버 및 프론트엔드)
* **프론트엔드 (고객 대시보드):** React, Vue.js, 혹은 Next.js 기반의 모던 웹 사이트입니다. 가입/로그인, Stripe 구독 결제 정보 변경, 헬스체크 URL CRUD 폼 등을 제공합니다.
* **백엔드 (중앙 API 서버):** 
  * 사용자 관리, 인증 토큰(JWT) 제어, 결제 트랜잭션을 관리합니다.
  * Go Checker들이 측정하여 던져주는 헬스체크 이력을 받아서 PostgreSQL에 영구 적재합니다.
  * 상태 전이가 감지되었을 때 비동기 알림 메시지 큐(RabbitMQ/Redis)를 통제하여 슬랙/디스코드/SMS 등으로 🚨 알림을 쏩니다.

### 3.3 분리 아키텍처의 장점
* **신뢰성 극대화 (False Alert 방지):** 서울 노드와 미국 노드가 **동시에 헬스체크 실패**를 보고할 때만 최종 OFFLINE으로 규정하여 슬랙 알림을 쏨으로써, 1개 수집 서버 망 장애로 인한 허위 알림(False Alert)을 차단합니다.
* **인프라 비용 최소화 (Scale-out):** 고객 및 타겟 수가 폭증해도 메인 웹 서버는 그대로 둔 채, 매우 저렴한 Go Checker 인스턴스의 개수만 수평 확장해주면 되므로 운영 비용을 획기적으로 낮출 수 있습니다.

## 4. 핵심 차별화 마케팅 포인트

레드오션인 모니터링 시장에서 살아남기 위한 `go-watchdog`만의 엣지(Edge) 포인트 기획입니다.

1. **미려한 다크모드 대시보드 기본 제공:**
   * 기존 UptimeRobot 등 투박한 디자인의 경쟁사 대비, go-watchdog의 최고 강점인 **글래스모피즘(Glassmorphism) 기반 비주얼 대시보드**를 마케팅 전면에 내세워 개발자들의 시각적 니즈를 저격합니다.
2. **공개 상태 페이지 (Public Status Page):**
   * 유저들이 본인의 도메인(예: `status.mycompany.com`)을 당사 서비스에 매핑하여, 자사 고객들에게 서비스의 실시간 작동 여부와 월간 가동률(Uptime %)을 보여주는 미려한 페이지를 쉽게 커스터마이징하고 생성할 수 있게 합니다. (유료 등급의 강력한 킬러 기능)
3. **SSL 인증서 만료 알림 서비스:**
   * 헬스체크 시 대상 서버의 SSL 인증서 만료 예정일(예: 30일 전, 7일 전)을 함께 파싱해 두었다가, 만료 임박 시 알림을 보내주는 편의 기능을 탑재합니다.

## 5. 로드맵 및 개발 1단계 (MVP)

이 비즈니스를 최소한의 비용으로 시장 검증(MVP, 최소 기능 제품)해보기 위한 1단계 개발 마일스톤입니다.

* **기간:** 4주
* **목표:** 회원가입 + 헬스체크 등록 + 슬랙 알림 + Stripe 구독 결제 연동 검증
* **사용 기술 스택:**
  * **Backend:** Go (Goroutine 기반 스케줄러 내장)
  * **Frontend:** Vue.js 또는 React (미려하고 반응성 높은 UI)
  * **Database:** PostgreSQL (안정성 확보)
  * **Infrastructure:** AWS Lightsail 또는 OCI Free Tier (초기 인프라 비용 최소화)
